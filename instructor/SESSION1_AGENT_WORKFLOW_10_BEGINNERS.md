# 10명 초급자용 120분 강의안 — AI 에이전트 문제해결 직접 시연과 실습

일시: 2026년 8월 14일 19:00~21:00  
대상: SK하이닉스 취업 희망 대졸자 10명  
현재 수준: 바이브 코딩 입문, GitHub 계정 미보유자 포함  
사용 도구: Antigravity + Claude Code 또는 Codex + GitHub

## 1. 강의 목표

이 강의는 SK하이닉스 면접장의 LLM을 재현하는 수업이 아니다. 더 강력한 AI 에이전트를 이용해 반도체 문제를 조사·분석·검증·기록하는 전 과정을 직접 보여주고, 수강생이 작은 단계 하나를 수행하도록 하는 수업이다.

수업 종료 시 수강생은 다음을 설명할 수 있어야 한다.

1. 일반 채팅과 AI 에이전트의 차이
2. 문제를 Agent에 던지기 전에 사람이 정해야 하는 항목
3. Antigravity의 조사 결과를 Claude Code/Codex에 넘기는 방법
4. AI가 만든 코드·그래프·주장을 사람이 검증하는 방법
5. 이 과정을 자신의 AI 활용 경험과 포트폴리오로 발전시키는 방법

## 2. 성공 기준을 두 단계로 나눈다

### 전원 필수 성공

- 자신의 직무 문제를 `사용자·데이터·결정` 한 문장으로 작성
- Antigravity 또는 강사 화면에서 출처 있는 근거카드 구조 이해
- Claude Code/Codex에 저장소를 먼저 읽게 하는 프롬프트 실행 또는 관찰
- AI 답변에서 확인된 사실·가설·미확인을 구분
- 수업 후 혼자 반복할 7일 계획 작성

### 준비된 학생만 추가 성공

- 개인 GitHub Fork·Clone
- 교육용 CSV 감사 실행
- Agent로 최소 변경
- `git diff` 확인과 Commit·Push

GitHub Pages 배포는 120분의 전원 필수 목표가 아니다. 강사가 전체 과정을 시연하고, 준비된 학생은 따라 하며, 나머지는 수업 후 가이드로 완성한다.

## 3. 강의 전 필수 준비

### 학생

- GitHub 계정 생성과 이메일 인증

GitHub 계정 생성은 이메일 인증·사용자명 충돌·보안 확인 때문에 수업에서 일괄 처리하지 않는다. 계정이 없는 학생은 사전에 반드시 만들게 한다.

### 강사

- GitHub 미가입·Agent 미로그인 학생 명단 사전 확인

## 4. 수업의 한 줄 서사

> 문제를 좁힌다 → Antigravity로 근거를 찾는다 → 근거카드를 Agent에 인계한다 → Claude Code/Codex가 저장소를 읽고 분석한다 → 사람이 diff·수치·반례를 검증한다 → GitHub에 과정의 증거를 남긴다.

## 6. 120분 진행표

### 00~10분 — 채용 변화와 오늘의 목표

보여줄 내용:

- SK하이닉스는 AI 활용 역량과 직무 전문성을 함께 본다.
- 설명회 정리상 Half-day 문제해결 PT에서는 화면 내 LLM을 사용할 수 있다.
- 그러나 오늘은 면접 도구를 복제하지 않고, 더 강한 Agent로 실제 경험을 만드는 방법을 배운다.
- 문제를 만나자마자 AI에 정답을 요구하지 않는다.
- 자신의 전공지식에서 중요한 변수·물리법칙·공정 순서·고장 메커니즘을 먼저 꺼낸다.
- `PLAN.md`에는 이번 문제의 목표·가설·단계·검증 기준을 적고, 검증된 반복 절차만 `SKILL.md`로 일반화한다.

질문:

> AI에게 무엇을 시켰는지가 아니라, AI의 답 중 무엇을 왜 믿었는지 설명할 수 있는가?

칠판에 다음 흐름을 적는다.

```text
문제 → 전공 키워드 → PLAN.md → AI 질문·반박 → 데이터 검증 → SKILL.md
```

Photo 사례의 전공 키워드는 답이 아니라 탐색의 출발점으로만 제시한다.

```text
Dose · Focus · PR tone · PEB · CD/CDU · 공정 Window · Tool/Field
```

강사 멘트:

> “PLAN.md는 AI가 마음대로 달리지 않게 만드는 이번 문제의 작업계획입니다. SKILL.md는 한 번의 답을 복사하는 문서가 아니라, 여러 문제에서 검증된 해결 절차를 재사용하기 위한 문서입니다. 그 사이에서 여러분은 AI에게 근거와 반대 가설을 계속 물으며 계획을 고칩니다.”

### 10~25분 — 강사의 전체 Agent Workflow 라이브 시연

강사는 학생에게 따라 하게 하지 않고 먼저 전체 결과를 보여준다.

1. 문제정의 문장 작성
2. Antigravity에서 공식 문서·논문 탐색
3. `research/SOURCES.md` 근거카드 작성
4. Claude Code/Codex에 저장소 규칙과 근거카드 읽게 하기
5. 데이터 감사·그래프 생성
6. AI의 잘못된 해석 하나 발견·수정
7. 테스트, `git diff`, Commit
8. GitHub Pages 결과 제시

연결 멘트:

> “방금 본 것은 버튼 여덟 개가 아니라, 질문과 근거가 다음 Agent로 전달되는 하나의 작업 흐름입니다.”

### 35~52분 — Antigravity 근거 조사 실습

페어 중 한 명이 실행하고 다른 한 명은 결과를 감사한다.

```text
주제: [주제]
사용자 결정: [결정]

이 문제와 관련된 전공 원리, 변수 정의, 지배식 또는 도메인 제약,
대표 분석법과 한계를 조사하라.
공식 문서·교재·논문 원문을 우선하라.
각 출처에 원문 URL, 저자·기관, 확인한 사실, 적용 범위,
이 자료만으로 말할 수 없는 내용을 구분하라.
코드와 최종 결론은 만들지 마라.
```

페어의 검수 질문:

- 원문 링크가 실제로 열리는가?
- 원문이 정말 그 주장을 말하는가?
- 변수 단위와 적용 조건이 있는가?
- AI가 검색 요약을 사실로 확대하지 않았는가?

산출물: 근거카드 1개. 완벽한 문헌조사보다 출처와 한계를 구분하면 성공이다.

### 52~60분 — Agent 인계 패킷 만들기

```text
문제:
사용자 결정:

입력 후보:

주가설:
대안가설:
현재 말할 수 없는 것:
완료 기준:
```

설명:

> Agent 사이의 성능 차이보다 인계 패킷의 품질이 결과를 크게 바꾼다. 긴 대화 전체를 넘기지 말고 확인된 사실과 다음 작업만 넘긴다.

### 60~80분 — Claude Code/Codex 저장소 이해와 계획 실습

준비된 학생은 자신의 Fork에서, 미준비 학생은 페어의 노트북에서 실행한다.

```text
AGENTS.md, README.md, research/SOURCES.md와 데이터 사전을 먼저 읽어라.
아직 파일을 수정하지 마라.
문제·확인된 사실·가설·대안가설·미확인을 분리하라.
데이터 감사 → 기준 분석 → 그래프 → 오차 사례 → 보고서 순서로
최소 실행계획을 작성하라.
각 단계에 사용할 실제 파일, 명령, 성공 기준을 적어라.
저장소에 없는 파일·수치·공정 사실은 만들지 마라.
```

초급자 관찰 포인트:

- Agent가 실제 파일을 읽는가?
- 바로 코드를 만들지 않고 계획부터 세우는가?
- 사용자의 결정을 잊지 않았는가?
- 대안가설과 실패 조건이 들어 있는가?

### 80~98분 — 작은 실행과 인간 검증

강사는 한 페어만 대표로 화면 공유한다. 모든 페어가 동시에 복잡한 코드를 만들지 않는다.

요청 예시:

```text
교육용 데이터의 원본을 수정하지 말고 다음만 수행하라.
1. 행·열, 결측, 중복, 수치 범위, Tool별 표본 수를 계산한다.
2. CD 분포와 Tool별 CD를 보여주는 그래프 하나를 만든다.
3. 관찰 사실과 가능한 설명을 분리한다.
4. 실행 명령과 출력 파일을 보고한다.
요청 밖의 리팩터링과 새 모델 학습은 하지 마라.
```

사람 검증:

- 입력 행 수와 출력 행 수가 맞는가?
- 결측·중복 숫자를 직접 다시 계산할 수 있는가?
- 그래프 축·단위·표본 수가 표시되는가?
- Tool 차이를 원인이라고 단정하지 않았는가?
- 원본 파일이 변경되지 않았는가?

시간이 부족하면 코드를 끝내지 않는다. **계획, 명령, 검증 체크리스트까지 작성하면 실습 성공**으로 처리한다.

발표 순서:

3. AI 답에서 무엇을 의심했는가

꼬리질문:

- AI의 첫 답 중 무엇을 버렸는가?
- 상관관계의 대안 설명은 무엇인가?
- 다른 Tool에서 결과가 반대라면 무엇을 바꿀 것인가?
- 본인이 한 판단은 정확히 무엇인가?

## 7. 시간 부족 시 축소 순서

시간이 부족하다고 핵심 검증 단계를 삭제하지 않는다. 아래 순서로 산출물 범위를 줄인다.

1. GitHub Pages 개인 배포를 수업 후로 이동
2. 모든 페어의 코드 실행을 1개 대표 시연으로 축소
3. 발표를 2개 페어만 진행하고 나머지는 문서 제출
4. 그래프를 5종이 아니라 1종으로 축소
5. 근거카드를 3개가 아니라 1개로 축소

끝까지 유지할 것:

- 문제정의
- 출처와 한계 구분
- Agent 인계 패킷
- AI 출력의 인간 검증
- 본인 판단 설명

## 8. GitHub 계정이 없는 학생 대응

### 수업 전

- 사전 준비서의 계정 생성 절차를 보내고 이메일 인증까지 요구한다.
- GitHub ID를 사전 설문 필수항목으로 둔다.
- 계정 생성 실패자는 이유를 수업 3시간 전까지 알리게 한다.

### 수업 중

- 계정 생성에 전체 수업을 멈추지 않는다.
- 미가입자는 준비된 학생과 페어로 조사·질문·검증 역할을 수행한다.
- Commit·Push는 페어의 준비된 학생이 화면을 공유한다.
- 미가입자는 수업 후 24시간 안에 계정을 만든 뒤 개인 Fork를 제출한다.

GitHub는 채용 지원의 필수 제출물이라고 단정하지 않는다. 이 수업에서는 **과정·수정·검증의 증거를 남기는 교육 도구**로 사용한다.

## 9. 일반 채팅과 Agent의 차이를 보여주는 시연

### 일반 채팅에 묻기

```text
Photo 공정 CD 산포 원인을 알려줘.
```

예상 문제:

- 일반론 나열
- 데이터와 저장소를 보지 않음
- 출처·단위·검증 기준 부족
- 실행 결과가 남지 않음

### Agent에 작업시키기

```text
저장소 규칙과 데이터 사전을 먼저 읽어라.
원본을 수정하지 마라.
CD 산포의 관찰 사실·가설·대안가설을 분리하라.
결측·Tool 편중·시간 Drift를 먼저 감사하라.
수정 전 성공 기준과 변경 파일을 제시하고,
승인된 범위만 구현한 뒤 테스트·diff·한계를 보고하라.
```

차이:

- Agent는 파일을 읽고 도구를 실행하며 결과를 저장한다.
- 그러나 Agent도 틀릴 수 있으므로 사람이 범위·근거·검증을 통제한다.
- 좋은 경험은 `AI가 만들었다`가 아니라 `내가 문제와 검증 루프를 설계했다`로 설명한다.

## 10. 강사의 마지막 메시지

> 오늘 두 시간에 웹앱 하나를 완성하지 못해도 괜찮습니다. 대신 문제를 좁히고, 근거를 찾고, Agent에 정확히 인계하고, 결과를 의심하고 검증하는 순서를 가져가야 합니다. 이 순서를 일주일 반복하면 지원서 문장이 아니라 면접에서 직접 설명할 수 있는 경험이 남습니다.
