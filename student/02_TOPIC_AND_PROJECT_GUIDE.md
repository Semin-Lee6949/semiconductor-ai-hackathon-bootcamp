# 2단계 실무 가이드 — 주제 선정과 프로젝트 착수

목표: “AI 모델을 하나 써보자”가 아니라 **반도체 현장 사용자가 숫자를 보고 어떤 결정을 더 잘 내리게 할지** 정합니다.

## 1. 좋은 주제의 한 문장 구조

```text
[사용자]가 [공정·설비 상황]에서 [입력 데이터]를 이용해
[결정]을 내릴 때 [KPI]와 [위험]을 함께 보여주는
[플랫폼 또는 시뮬레이터]를 만든다.
```

예시:

```text
CMP 공정 엔지니어가 Down Force·속도·Pad Age 조건에서
Removal Rate만 높이는 대신 WIWNU·Dishing 위험을 함께 비교해
Robust Recipe 후보와 추가 측정 조건을 고르는 시뮬레이터를 만든다.
```

나쁜 예시:

- “머신러닝으로 수율을 예측한다.” — 사용자 결정이 없음
- “반도체 Digital Twin을 만든다.” — 일주일 범위를 초과함
- “딥러닝을 적용한다.” — 문제보다 모델명이 앞섬

## 2. 25분 주제선정 절차

### 0~5분 — 지원 직무에서 시작

내가 설명하고 싶은 직무 역량을 하나만 고릅니다.

- 공정기술: Recipe, Window, 균일도, 결함, 추가 DOE
- 소자: 분포, 산포, Vth, Ion/Ioff, Retention risk
- 양산기술: Drift, 이상 Lot, Yield risk, 조치 우선순위
- 설비기술: 센서 이상, Fault 유형, 점검 순서, 검출 지연

### 5~10분 — 사용자 결정 하나 선택

다음 중 하나만 고릅니다.

- 어떤 Recipe 후보를 먼저 시험할 것인가?
- 어떤 Lot·Tool을 먼저 확인할 것인가?
- 어떤 센서를 먼저 점검할 것인가?
- 어떤 공정 Window가 변화에 강한가?
- 어떤 보정량을 다음 Run에 적용할 것인가?
- 어느 조건에서 추가 측정이나 DOE가 필요한가?

### 10~15분 — 후보 2개 점수화

각 항목을 0~3점으로 평가합니다. 총점보다 **0점 항목**이 중요합니다.

| 항목 | 0점 | 1점 | 2점 | 3점 |
|---|---|---|---|---|
| 직무 연관 | 설명 불가 | 간접 관련 | 관련 있음 | 내 경험·관심과 직접 연결 |
| 사용자 결정 | 없음 | 모호함 | 하나로 정의 | 입력 변화에 따라 행동이 달라짐 |
| KPI | 없음 | 하나지만 불명확 | 측정 가능 | 성능과 위험을 함께 측정 |
| 데이터 | 목표열 없음 | 품질 문제 큼 | 분석 가능 | Holdout과 교란 검증 가능 |
| 상호작용 | 정적 그래프 | 필터 하나 | 입력 두 개 | What-if와 전후 비교 |
| 7일 완성성 | 불가능 | 범위 축소 필요 | 가능 | 기준모델·검증·배포까지 가능 |

선정 원칙:

- 14점 이상: 진행 후보
- 10~13점: 범위를 한 단계 축소
- 9점 이하: 다른 주제 선택
- 사용자 결정·데이터·7일 완성성 중 하나라도 0점이면 탈락

### 15~20분 — 데이터 먼저 열기

모델을 선택하기 전에 `train.csv`를 확인합니다.

```text
행·열은 몇 개인가?
목표변수는 무엇인가?
단위가 섞였을 가능성은 있는가?
결측·중복·극단값은 어디에 몰려 있는가?
Tool·Lot·시간별 표본 수가 편중됐는가?
A/B의 결론이 같을 것이라고 가정하고 있지 않은가?
```

### 20~25분 — 1페이지 Project Card 작성

`PLAN.md`를 다음 수준으로 채웁니다.

```text
문제:
실제 사용자:
사용자가 내릴 결정 1개:
핵심 KPI 1~2개:
함께 제한할 위험 KPI 1~2개:
기준모델:
개선모델 후보:
조작할 입력 2~4개:
주가설:
대안가설:
교란 가능성:
완료조건:
하지 않을 것:
```
## 3. 10개 프로젝트 선택 지도

| 번호 | 주제 | 핵심 사용자 결정 | 최소 KPI | 권장 난이도 |
|---|---|---|---|---|
| 01 | Photo PR Coat–Expose–Develop | PR tone별 두께·Dose·PEB·현상 Margin | CD, CDU, LER, Scum, Collapse | 기본 |
| 02 | Overlay 보정 | 보정계수와 Hot Spot 점검 | Residual, 합격률 | 기본 |
| 03 | Dry Etch Endpoint | Endpoint·Over-etch 조건 | CD bias, Selectivity | 중급 |
| 04 | HAR Etch Profile | Bowing·Taper 제한 조건 | Depth, Sidewall, Bowing | 고급 |
| 05 | CMP 최적화 | Robust Recipe 후보 | RR, WIWNU, Dishing | 기본 |
| 06 | 증착 APC | 다음 Run 보정량 | Thickness error, Uniformity | 중급 |
| 07 | FDC | 점검할 Tool·센서 우선순위 | Recall, False alarm, Delay | 중급 |
| 08 | DRAM 소자 | 산포에 강한 Window | Vth, Ion/Ioff, Yield | 중급 |
| 09 | 3D NAND | Read reference와 위험조건 | Window, BER proxy | 고급 |
| 10 | Virtual Lot | 병목 공정과 추가실험 | Final CD, Risk, Yield | 고급 |

처음 코딩하는 수강생은 01·02·05 중 하나를 권장합니다. “어려운 주제”보다 **검증된 작은 제품**이 더 좋은 결과물입니다.

## 4. 데이터에서 의미를 찾는 순서

### 질문 1 — 데이터가 믿을 만한가?

- 결측과 중복은 얼마나 되는가?
- 단위가 다른 값이 섞였는가?
- 극단값은 센서 오류인가, 희귀 조건인가?
- 특정 Tool·Lot에 데이터가 몰렸는가?

### 질문 2 — 신호가 반복되는가?

- 전체 데이터의 관계가 Tool별로도 유지되는가?
- 시간 뒤쪽 Holdout에서도 유지되는가?
- 이상치를 제외하기 전후 결론이 같은가?
- 단순 기준모델보다 실제로 나은가?

### 질문 3 — 행동으로 연결되는가?

- 결과가 달라지면 사용자의 다음 행동도 달라지는가?
- 추천 조건의 위험과 불확실성을 함께 표시하는가?
- 실제 적용 전에 필요한 추가 측정·DOE를 말하는가?

## 5. 기준모델부터 만드는 이유

개선모델만 보여주면 AI가 실제로 기여했는지 판단할 수 없습니다.

권장 기준모델:

- 회귀: 전체 평균, 단순 선형회귀
- 분류: 다수 클래스, 단순 임계값
- 시계열: 이전 Run 값, 이동평균
- 최적화: 현재 Recipe 또는 단일 KPI 최대화

비교할 것:

- Holdout 성능
- 중요한 오차 사례 3개
- Tool·Lot·시간 구간별 성능
- 데이터 정제 전후 성능
- 복잡도 증가에 비해 얻은 개선

## 6. MVP 범위 고정

필수 기능은 여섯 개뿐입니다.

1. 샘플 데이터 선택 또는 CSV 입력
2. 결측·중복·이상치·편중 진단
3. 기준모델과 개선모델 비교
4. 입력 2개 이상의 What-if 조작
5. 위험도·추천·추가실험 제안
6. 한계와 인간 검증 기록

이번 프로젝트에서 하지 않을 것:

- 실제 Fab 연동
- 실시간 장비 제어
- 대규모 딥러닝 학습
- 10개 공정을 모두 연결
- 모델 종류를 많이 나열
- 검증되지 않은 경제효과 산정

## 7. Codex 착수 프롬프트

### 프롬프트 A — 수정 없는 진단

```text
AGENTS.md와 PLAN.md를 읽어라.
코드는 수정하지 마라.
내 train.csv에서 먼저 확인해야 할 스키마, 결측, 중복, 단위,
이상치, Tool/Lot/시간 편중과 목표 누출 위험을 체크리스트로 만들어라.
각 항목을 검증할 실제 파일과 명령을 제시하라.
```

### 프롬프트 B — 주제 범위 검토

```text
PLAN.md의 사용자, 결정, KPI, 가설을 검토하라.
7일 개인 프로젝트로 너무 큰 범위를 지적하고,
필수 기능 6개를 만족하는 최소 MVP로 줄여라.
모델명보다 사용자 결정과 검증 기준을 우선하라.
아직 코드를 수정하지 마라.
```

### 프롬프트 C — 구현 계획

```text
현재 저장소 구조를 유지하면서
데이터 감사 → 기준모델 → 개선모델 → artifacts JSON → docs 웹앱 → 테스트
순서의 실행계획을 작성하라.
단계마다 성공 기준, 변경 파일, 실행 명령을 명시하라.
요청과 무관한 리팩터링은 금지한다.
```
